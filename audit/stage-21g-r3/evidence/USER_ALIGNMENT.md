# 用户需求对齐

## 我理解你要做什么

你已批准一个仅供本地 TEST_ONLY 演练的库存 CSV 汇总小项目。程序使用 Python 标准库，读取 `sku,delta` 两列；`delta` 可正可负且必须是整数；同一 SKU 的数值相加；结果按 SKU 排序。列数错误、空 SKU、非法整数都必须报错，不能在失败时输出看似成功的汇总。项目还要有真实的 `unittest` 测试。

必须保留的限制：不使用第三方依赖；程序、测试和夹具不得联网或读取生产数据，不调用外机，不部署生产；使用当前已指定的本地 scratch Git 仓库，不使用 Hermes/P1 生产源码。实验可冻结 TEST_ONLY 规格、记录实验 Gate，但不能把它说成生产审批或正式外部盲审。只有复现出缺陷时才进行模拟整改。

## 准备采用什么策略、为什么这样选

先把输入规则、汇总行为、错误行为和测试验收写成可检查的候选规格，再由调度端按已批准的实验需求核对并记录 TEST_ONLY 冻结。这样能让后续实现和测试针对同一组明确规则；冻结只对本地实验有效，不改变生产审批状态。

采用标准库和小范围模块边界，符合用户限制并避免不必要依赖。失败输入作为明确验收项，要求程序报告错误且不呈现部分或伪造的成功汇总。

## 系统会怎么运转

1. 用户或调用者提供 CSV 输入，字段为 `sku,delta`。
2. 命令行程序校验每行字段数量、SKU 非空以及 delta 可解析为整数；遇到无效输入即报告错误并以失败状态结束，不给出成功汇总。
3. 全部输入有效后，程序按 SKU 累加 delta，并按 SKU 排序输出汇总。
4. `unittest` 测试分别检查正常汇总、正负累计、排序，以及各类无效输入的错误结果。
5. 调度端检查候选规格与用户已批准的 TEST_ONLY 需求一致后，记录实验规格冻结，再交给后续获授权角色实施和审查。具体角色顺序与 PRE/POST 条件依照已授权的调度方案；本文件不代替调度或审批。

## 整体架构如何分工

基线仓库目前只有用户需求和 TEST_ONLY 授权文件，没有业务程序、测试或既有模块可复用。以下均为拟新建职责，不是当前已有组件：

- 命令行入口：读取输入、调用汇总逻辑、呈现成功结果或错误状态。
- CSV 解析与校验：识别两列记录，拒绝列数错误、空 SKU 和非整数 delta。
- 汇总逻辑：累计相同 SKU 的整数 delta，并生成按 SKU 排序的结果。
- 单元测试：通过 Python 标准库 `unittest` 检查成功与失败行为。

以上职责可以由少量本地模块承载；模块文件名、输入来源（文件或标准输入）、命令行参数和具体错误文案尚未由用户指定，应由实现者在不改变已批准行为的前提下采用简单一致的方案。

## 完成后你会得到什么、如何验收

实验完成时应有可运行的本地 CLI、标准库实现、真实 `unittest` 测试和可追溯的实验记录。验收检查：正负 delta 正确累计；相同 SKU 合并；SKU 排序稳定；列数错误、空 SKU、非法整数均明确失败且不输出成功汇总；测试确由 `unittest` 执行；依赖与运行范围符合本地 TEST_ONLY 限制。

当前候选规格尚未冻结，也没有生产 Gate 批准。调度端可按已批准的实验需求检查并记录 TEST_ONLY 冻结；这不需要另行取得生产审批，也不得表述为生产批准。

## 未决事项

- QUESTION：错误信息的具体文字及退出码未指定。建议统一错误输出到标准错误流并使用非零退出码；这是实现建议，需由规格审查确认，不改变“必须报错且不得伪成功”的已批准要求。
- QUESTION：空输入及只有表头的输入如何处理未指定。建议视为有效的空汇总；这是建议，须在冻结前确认。
